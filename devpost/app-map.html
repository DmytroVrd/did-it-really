Did it really? — App Map

A take-home guide to the finished proof of concept: what the pieces are, where one check travels through the code, and where to start a change.

What it is

A local Flask web app. You paste a coding agent's final report and the path to a git repository, pick the agent session, and get every claim back as ✓ VERIFIED, ✗ NOT FOUND or ! UNVERIFIABLE, with evidence from the diff and a list of changes the agent never mentioned.

Pagetemplates/index.html, static/app.js, static/style.css — form, presets, rendering the result.
Serverapp.py — validates input, turns a preset into a start time.
Git readerchanges.py — plain git commands → what actually changed.
Verifierverifier.py — one Gemini call, then Python checks the AI's work.

One check, end to end

Solid green border: plain Python, deterministic and tested. Dashed orange: the only AI step — everything it says is checked afterwards.

Reference route: the "I left config.py untouched" lie

A reference route through the real code (a snapshot — search the anchors if line numbers drift).

  1. Collect the truth. changes.py → collect_changes. With a session preset it diffs from the last commit before that time, plus uncommitted and untracked files. Every git call goes through git() with UTF-8 decoding.
  2. Separate the denial. verifier.py → FILE_UNTOUCHED and split_special_claims. Whatever Gemini returned, "I left config.py untouched" becomes its own claim tied to config.py.
  3. Judge it in Python. verifier.py → judge_untouched_claims: config.py is in the diff, so ✗ with config.py's own changed lines as evidence. _mentioned ignores names inside denials, so config.py also lands in "Changes the agent didn't mention".
The test that pins this down

tests/test_untouched_claims.py → test_bug_report_scenario and test_file_named_only_in_denial_is_unmentioned. Run:

python -m pytest tests/test_untouched_claims.py -k "bug_report or denial_is_unmentioned" -v

A practice to reuse

Write the observable result first, then pin each surprise with a test from a real case.

The PRD criterion prd.md > Changes the Agent Didn't Mention said what you should see when an agent changes a file quietly. Running the app on a real repository (my-check-repo) showed a case the plan hadn't covered: "I left config.py untouched" was explained with the wrong file. The fix started by adding one concrete criterion to the PRD and a test reproducing the exact case (test_bug_report_scenario), then changing verifier.py until it passed — and re-running the real repo.

Next project: for each feature, write one "you should see…" sentence before asking an agent for code, and when something surprises you, turn that exact input into a test before the fix.
